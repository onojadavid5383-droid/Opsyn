1. Executive Overview
The Opsyn Form Schema Builder is a configuration-driven metadata system that allows organization administrators to design, version, and deploy data collection forms entirely from the frontend — without any code changes. It is the foundational layer that makes Opsyn a genuinely multi-tenant, enterprise-grade platform.
Rather than hardcoding forms for each use case (customer intake, GIS surveys, field technician reports, infrastructure uploads, approval checklists), the platform stores form definitions as structured metadata. The frontend reads those definitions at runtime and renders the appropriate UI. The backend validates submitted data against the same definitions. Every module in Opsyn — past, present, and future — uses this single system.
1.1 The Problem This Solves
Without Form Builder
With Form Builder
Adding a new data field requires a backend migration, a new API endpoint, and a new frontend component — minimum 1–2 days of engineering work.
An admin adds a field in the UI in 30 seconds. It is live immediately for the correct department, stage, and role.
Every tenant has the same fields even if their business process is different.
Every tenant defines their own schema. Tenant A collects 12 customer fields. Tenant B collects 7 different ones.
Forms are scattered across modules with inconsistent validation logic.
One validation engine, one submission format, one audit trail — across every form in the system.
Infrastructure upload validation is hardcoded in router.py — changing it requires deployment.
Infrastructure upload column requirements are read from the schema — an admin edits them in the UI.
Pipeline stages cannot require dynamic field completion — it must be coded per stage.
Any pipeline stage can require any form schema to be completed — configured in the UI, enforced by the engine.
1.2 Design Philosophy — Three Non-Negotiables
Schema-first: the definition of a form is always the source of truth. The UI renders from it. The API validates against it. Reports are generated from it. Nothing hardcoded anywhere.
Version-immutable: once a schema version is published, it is never mutated. Old submissions are always readable because they reference the exact version they were created under.
Association-driven: a form schema is only useful in context. The association system is what connects a schema to a module, a pipeline stage, a department, or an external trigger — making the form appear in the right place at the right time.

2.2 How a Form Gets From Builder to User
Admin opens Form Builder → creates schema 'Customer Intake' → adds 8 fields → publishes → system creates schema_version 1.
Admin opens Association Manager → links 'Customer Intake' schema to the Customer module and to Pipeline Stage 1 (Finance Department).
A field technician app fires an external task to create a customer. The platform finds the active 'Customer Intake' schema for that tenant and module. Returns the schema definition to the frontend.
Frontend Form Renderer reads the field definitions and renders the correct input components (text box, number input, date picker, dropdown, etc.) in the configured order.
User submits. API receives { schema_id, schema_version, entity_id, data: {...} }. Validation Engine checks every field. On success, writes to form_submissions as JSONB. On failure, returns field-level errors.
Pipeline stage advancement check queries form_submissions for required schemas linked to this stage. If any mandatory schema has no valid submission, advancement is blocked.

4. Validation Engine — Deep Design
4.1 Engine Architecture
The Validation Engine is a pure stateless function. It takes a schema version snapshot and a submitted data object, runs every field through its validation rules, and returns a structured result. It never writes to the database. It can be called from any API endpoint, any background job, or even the frontend (as a preview).
validate(schema_version_snapshot: FieldDefinition[], data: dict, context: ValidationContext) -> ValidationResult
Input
Type
Description
schema_version_snapshot
FieldDefinition[]
Complete list of field definitions for the version being validated against. Taken from field_snapshot JSONB of the version record.
data
dict
Submitted key-value pairs. Keys are field_key strings. Values are raw submitted values.
context
ValidationContext
Carries: tenant_id, submitting_user_role, current_pipeline_stage_order, is_draft (draft submissions skip required-field checks).
Output Field
Type
Description
is_valid
boolean
True only if zero errors across all fields
errors
FieldError[]
List of {field_key, field_label, error_code, message} — one entry per failing rule per field
warnings
FieldWarning[]
Non-blocking notices (e.g., coordinate (0,0) warning)
coerced_data
dict
Validated and type-coerced data ready for storage — integers parsed, dates normalized to ISO, etc.
missing_required_fields
string[]
field_keys of required fields not present in submitted data
4.2 Validation Pass Order
Type coercion: attempt to coerce submitted value to the field's declared type. If coercion fails (e.g., 'abc' submitted for an integer field), record a type_error and skip further rules for that field.
Required check: if field is required and value is null/empty after coercion, record required_error.
Conditional visibility: if field is conditionally hidden by conditional_logic and the conditions are met, skip validation entirely for that field — hidden fields cannot be required.
Stage-based required check: if context.current_pipeline_stage_order >= field.stage_required_at and value is empty, record stage_required_error.
Role-based edit check: if submitting user's role is not in field.role_editable, ignore submitted value — do not validate it, do not store it. Silently drop it.
Validation rules: evaluate all applicable rules from validation_rules JSONB in order: length → range → pattern → enum membership → date constraints → uniqueness (DB check).
Conditional logic evaluation: if a field's conditional_logic has action='require', apply required check only when conditions are met.
4.3 Dual Validation — Frontend Preview + Backend Authority
The validation engine runs in two places:
Frontend (TypeScript port): runs on field blur and on submit-attempt. Gives instant feedback. Uses the schema definition fetched from the API. Prevents obviously invalid submissions reaching the server.
Backend (Python, authoritative): runs on every POST /submissions call. The frontend validation is a UX convenience — the backend validation is the source of truth. Any discrepancy means the backend wins.
💡  The frontend validation config is generated from the same field_definitions data the backend uses — served by GET /forms/schemas/{id}/renderer-config. This guarantees they are always in sync.

6.3 Publishing Workflow in the UI
Admin works on schema in draft mode. Canvas shows a yellow DRAFT badge.
Click 'Publish Schema' button. System shows a diff preview: fields added since last publish, fields changed, fields removed.
Admin enters optional changelog note: 'Added company registration number field for corporate customers.'
Confirm → API calls POST /schemas/{id}/publish → new version created → canvas shows version number and green PUBLISHED badge.
From this point, fields are locked (no edits). To make changes, admin clicks 'Create New Draft' → clones current field set into an editable draft → edit → publish again.

7. Form Renderer — Reusable Component
FormRenderer is a single React component used everywhere a form appears in the platform. It takes a schema definition and renders the correct UI. It is not aware of what the form is for — it just renders fields.
7.1 Component API
<FormRenderer
  schemaId={string}                   // Required — which schema to render
  entityType={string}                 // 'customer' | 'project' | ...
  entityId={string | null}            // Pre-fill from existing submission if present
  context={{ stage, role, dept }}     // Drives conditional field visibility
  onSubmit={(data) => void}           // Called with coerced data on valid submit
  onDraftSave={(data) => void}        // Called on auto-save (every 30s)
  readOnly={boolean}                  // Show values without edit capability
  showProgress={boolean}              // Show a progress bar: N of M required fields filled
  highlightMissing={boolean}          // Highlight unfilled required fields (for stage gate)
/>

7.3 Auto-Save & Draft System
Every 30 seconds while a user is filling a form, FormRenderer calls POST /submissions/draft silently.
On next open of the same form for the same entity, the renderer fetches the draft and pre-fills all fields.
A banner shows: 'Unsaved draft from 5 minutes ago — resume or discard?'
Draft submissions never trigger stage advancement checks — only final submissions do.
8. Integration with Existing Opsyn Modules
8.1 Customer Module Integration
The Customer module stops having hardcoded fields. Instead:
On tenant setup, the system checks if a schema associated with module='customer' and trigger_event='on_create' exists. If yes, it uses that schema for the customer creation form.
Customer detail page: GET /forms/context/module/customer/schemas returns all associated schemas. For each schema, FormRenderer is embedded in the appropriate tab.
Field values previously stored in customer_field_values are migrated to form_submissions JSONB. The field definitions move from hardcoded Python to the schema builder.
8.2 Pipeline Stage Integration
Each pipeline stage in the system has an id. When a stage is entered, GET /forms/context/pipeline_stage/{stage_id}/schemas returns all mandatory and optional forms for that stage.
The stage advancement validation currently in pipeline_service.py is extended: before allowing advance_stage, query form_submissions for all submissions where association_id matches a mandatory association for this stage and entity_id = project.id. If any mandatory schema has no valid submission with status='submitted', return HTTP 422 with the list of missing forms.
This replaces the current hardcoded stage_field_completion table with a generic, schema-driven check.
8.3 Infrastructure Upload Integration
The infrastructure upload validation engine (upload_service.py) currently hardcodes required column names and validation rules. After this module:
Each asset type (splitter, cabinet, OLT) has an associated form schema with machine_name = 'infra_splitter_upload', 'infra_cabinet_upload', etc.
The upload validator reads required columns and their types from the schema's field_definitions — not from hardcoded lists.
An admin can add a new required column to the upload format by adding a field to the schema in the UI — no code change, no deployment.
Excel error reports use field labels from the schema as column headers.
8.4 Audit Log Integration
Every form submission is logged to the existing infrastructure_audit_log (or a dedicated form_submission_audit_log) with:
actor_label resolved via the established pattern: (user.staff_profile.full_name if user.staff_profile else user.username) if user else 'System'
old_data: previous submission JSONB if this is an update
new_data: new submission JSONB
action: 'form_submitted' | 'form_updated' | 'form_approved' | 'form_rejected'
9. Implementation Phases
Nine phases, sequential. Each ends with a mandatory validation checkpoint before the next begins.
PHASE 1  Database Schema & Migrations   [Sprint 1 — ~3 days]
Objective

Write Alembic migrations in order: form_schemas → form_schema_versions → field_definitions → form_associations → form_submissions.

Severity
Mitigation
Schema version migration complexity — existing customer_field_values data does not map cleanly to form_submissions JSONB
High
Write a one-time data migration script in Phase 1 that transforms existing field values into form_submission rows against a seed schema version. Run on staging first. Rollback: restore customer_field_values table.
form_builder_router catch-all routes shadow existing task routes
High
Register form_builder_router before tasks_router in main.py. Add integration test that hits /api/v1/tasks/{id} after form router registration.
actor_label resolved as None in form submission audit log
High
All submission API handlers must fetch user with selectinload(User.staff_profile). Code review checklist item.
JSONB query performance degrades at high submission volume
Medium
GIN index on form_submissions.data. For reporting queries, consider a materialized view that flattens common schemas. Evaluate at 100k+ submissions.
Conditional logic evaluation on frontend and backend diverges
Medium
Generate frontend validation config from the same data as backend. Add integration test that submits data the frontend would consider valid and confirms backend also accepts it — and vice versa for invalid cases.
Admin deletes a field that has submitted data
Medium
Block hard delete if form_submissions.data JSONB for this schema contains the field_key in any row. Offer 'archive field' instead — field stays in field_snapshot, hidden from future forms, but historical data remains readable.
field_key changed after submissions exist
Medium
Lock field_key after first submission is recorded for this schema (not just after publish). Show warning if admin tries to edit key.
FormRenderer blank-page crash in a pipeline stage view
Medium
ErrorBoundary wraps FormRenderer everywhere. Fallback shows: 'Form could not be loaded — contact your administrator.' with the schema name for debugging.
Large forms (50+ fields) cause slow render
Low
Virtual scrolling in the Form Builder canvas for large schemas. FormRenderer renders sections on demand (collapsible sections lazy-render their fields).
