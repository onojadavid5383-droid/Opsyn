1. Executive Summary & Brainstorm Analysis
This document defines the complete implementation plan for the Opsyn Infrastructure Management Enhancement — specifically the ability to bulk-import, manage, and delete existing FTTH network assets including Splitter Boxes, Cabinets, OLTs, and Cable Routes within the multi-tenant Opsyn platform.
1.1 What This Module Must Achieve
Allow network operations teams to migrate existing deployed infrastructure into the platform via structured Excel uploads.
Support real-world FTTH telecom hierarchy — First-Level splitters (typically 1:8 or 1:16) feed Second-Level splitters (1:8 or 1:16), which feed customer ONUs. The system must model this hierarchy correctly and validate it.
Enforce a strict two-phase upload workflow: validate first, show a full preview report, then require explicit user approval before any data is committed to the database.
Provide batch deletion with the same two-phase approval gate — preventing accidental mass deletion.
Maintain a full audit trail of every upload and deletion action, consistent with the existing Opsyn audit log patterns.
Retain all existing Cable Routes upload logic unchanged; new asset types are additive.

1.3 Key Design Decisions from Brainstorm
Staging Table Pattern for Upload Safety
The two-phase workflow (validate → approve → commit) is best implemented using a staging table approach. Validated rows are written to infrastructure_upload_staging with a session_id. The user reviews the staging rows, approves, and the commit step moves them to the live tables atomically. This means no partially-committed uploads are possible — a rollback deletes the staging rows.
Splitter Hierarchy as a Self-Referential Relationship
The splitter_level field (First-Level or Second-Level) is not just metadata — it implies a structural relationship in the FTTH network. The database design must support a nullable parent_splitter_id on the splitter table, allowing a Second-Level splitter to be linked to its upstream First-Level splitter. This linkage is optional at upload time (existing infrastructure may not have this data) but the schema must support it for future use.
Deletion Uses box_id + splitter_level as Composite Key
The deletion spec requires matching on both box_id and splitter_level. This is intentional — the same box_id may theoretically exist at different levels in a network expansion scenario. The composite (box_id, splitter_level, tenant_id) forms the effective unique key for deletion matching.
Upload Sessions as First-Class Records
Every upload attempt — successful or not — is recorded in an infrastructure_upload_sessions table (analogous to external_task_logs in the existing system). This enables upload history, replay, and audit. Each session has a status: pending | validated | approved | committed | failed | rolled_back.
Error Report as Downloadable Excel
Validation errors are exported as a downloadable .xlsx file mirroring the input format with an extra Errors column. This allows operators to fix their source file and re-upload without manually identifying which rows failed.

3. Database Design
3.1 Design Principles
All tables: id (UUID PK), tenant_id (FK), created_at, updated_at, is_deleted (soft delete), created_by (FK → users.id).
GIS columns use PostGIS geometry(Point, 4326). Auto-generated via ST_SetSRID(ST_MakePoint(longitude, latitude), 4326).
Unique constraints are composite with tenant_id — e.g., UNIQUE(box_id, tenant_id) for splitters.
All JSONB columns (validation_errors, upload_payload) have GIN indexes.
Upload session tables follow the same pattern as external_task_logs in the existing system.

4. Validation Engine Design
4.1 Validation Layers
Validation runs in four sequential layers. A row failing any layer is marked invalid and included in the error report. Validation never stops early — all errors across all rows are collected in a single pass.
Layer
Name
What Is Checked
1
File-Level Validation
File extension is .xlsx; file is not corrupted (openpyxl can open it); file is not empty (has at least one data row beyond the header); file size does not exceed the configured limit (default 10MB).
2
Header Validation
All required column names are present (case-insensitive match); no required column is missing; extra columns are ignored with a warning.
3
Row-Level Data Validation
Required fields are not blank; numeric fields (input, output, capacity, number_tray, number_of_ODF, number_customer) are valid integers within allowed ranges; splitter_level is exactly 'First-Level' or 'Second-Level'; splitter_type is exactly 'PCC' or 'Legacy'; longitude is a valid float in range [-180, 180]; latitude is a valid float in range [-90, 90]; string fields do not exceed max length limits.
4
Database Validation
For each valid row, check whether a live (is_deleted=FALSE) record with the same unique key and tenant_id already exists. Flag as duplicate (not error) — duplicates are reported separately and excluded from the commit unless the user specifically enables overwrite mode.

6. Implementation Phases
Eight phases are defined below. Each phase has a validation gate checkpoint. No phase begins until the prior phase checkpoint is passed and approved.
PHASE 1  Database Migrations & Schema Setup   [Sprint 1 — ~3 days]
6.1 Phase 1 Objective
Create and migrate all database tables. Enable PostGIS extension if not already active. Establish index strategy. No API or UI work in this phase.
6.1.1 Backend Steps
Verify PostGIS extension is enabled on the PostgreSQL instance: CREATE EXTENSION IF NOT EXISTS postgis; Confirm in Alembic environment that geoalchemy2 is available.
Write Alembic migrations in dependency order: infrastructure_upload_sessions → infrastructure_upload_staging → infrastructure_deletion_sessions → splitter_boxes → cabinets → olts → infrastructure_audit_log.
Add columns to existing cable_routes table if needed (upload_session_id, is_deleted) for consistency. Do not break existing cable route data.
Add indexes: GiST index on all location (geometry) columns; GIN index on validation_errors JSONB columns; composite index (box_id, tenant_id) on splitter_boxes; composite index (cabinet_id, tenant_id) on cabinets; composite index (name, tenant_id) on olts.
Add DB-level CHECK constraints: splitter_level IN ('First-Level', 'Second-Level'); splitter_type IN ('PCC', 'Legacy'); longitude BETWEEN -180 AND 180; latitude BETWEEN -90 AND 90.
Seed test data for one test tenant: 3 splitters (2 First-Level, 1 Second-Level), 2 cabinets, 1 OLT. Used for duplicate detection tests in Phase 2.
6.1.2 Validation Gates
All migrations run on a clean database without error.
Rollback script returns schema to exact prior state.
PostGIS geometry columns created: SELECT type FROM geometry_columns confirms Point SRID 4326 for all location columns.
UNIQUE constraints enforced: attempt to insert duplicate box_id + tenant_id returns IntegrityError.
Seed data queryable; cross-tenant isolation confirmed.
Existing cable_routes table data is unchanged after migration.
🔴  Do not proceed to Phase 2 until a tech lead reviews and approves the migration scripts and confirms PostGIS is available in all environments.
PHASE 2  Validation Engine & Upload Service Backend   [Sprint 1–2 — ~4 days]
6.2 Phase 2 Objective
Build the core validation engine (upload_service.py), GIS utility functions (gis_utils.py), and the staging table logic. This is the most critical backend component — all upload safety depends on it.
6.2.1 gis_utils.py
Implement validate_coordinates(longitude, latitude) → returns (is_valid: bool, errors: list[str]). Checks: both values are present; both are numeric; longitude in [-180, 180]; latitude in [-90, 90]. Does NOT raise exceptions — returns error list for accumulation.
Implement make_point(longitude, latitude) → WKTElement('POINT(lng lat)', srid=4326) using geoalchemy2. This is the function used when building ORM model instances.
Implement warn_zero_island(longitude, latitude) → bool: returns True if coordinates are exactly (0, 0) — logged as a warning, not an error.
6.2.2 upload_service.py — Validation Engine
Implement validate_file(file: UploadFile) → FileValidationResult. Checks: file extension is .xlsx; file bytes are not empty; openpyxl can open the file without error; file size ≤ MAX_UPLOAD_SIZE_MB (configurable, default 10).
Implement validate_headers(sheet, required_columns: list[str]) → HeaderValidationResult. Case-insensitive match. Returns list of missing columns. If any required column missing, the entire file is rejected before row validation begins.
Implement validate_row_splitter(row_dict) → RowValidationResult. Checks all splitter fields per the rules in Section 4. Collects all errors in the row before returning.
Implement validate_row_cabinet(row_dict) → RowValidationResult. Cabinet-specific rules.
Implement validate_row_olt(row_dict) → RowValidationResult. OLT-specific rules.
Implement check_duplicate_splitter(db, box_id, splitter_level, tenant_id) → bool. Async query: SELECT 1 FROM splitter_boxes WHERE box_id=? AND splitter_level=? AND tenant_id=? AND is_deleted=FALSE. Returns True if duplicate.
Implement check_duplicate_cabinet(db, cabinet_id, tenant_id) → bool. Same pattern.
Implement check_duplicate_olt(db, name, tenant_id) → bool. Same pattern.
Implement run_full_validation(db, session_id, asset_type, file_bytes, tenant_id) → ValidationSummary. Orchestrates: file → headers → rows → duplicate checks. Writes all staging rows to infrastructure_upload_staging. Updates infrastructure_upload_sessions with counts and errors. Returns summary.
6.2.3 upload_service.py — Commit Logic
Implement commit_session(db, session_id, tenant_id, approved_by_user_id) → CommitResult. Must run in a single DB transaction. For each staging row where is_valid=True and is_duplicate=False: build ORM model instance, set location = make_point(longitude, latitude), set upload_session_id = session_id; INSERT into live table; write infrastructure_audit_log entry with action='upload'; mark staging row committed=True. On any exception, rollback entire transaction, set session status='rolled_back'. Return count of committed rows.
Actor label for audit log: resolve using the established pattern: (user.staff_profile.full_name if user.staff_profile else user.username) if user else 'System'. Use selectinload(User.staff_profile) in the user fetch query.
6.2.4 deletion_service.py
Implement validate_deletion_file(asset_type, file_bytes) → DeletionValidationResult. Parse .xlsx, check headers, build list of deletion keys from the file.
Implement match_deletion_keys_splitter(db, keys: list[{box_id, splitter_level}], tenant_id) → list[MatchResult]. For each key, query live table. Returns matched vs unmatched.
Implement match_deletion_keys_cabinet(db, keys: list[{cabinet_id, capacity}], tenant_id) → list[MatchResult]. Cabinet matching on both columns as per spec.
Implement execute_deletion(db, session_id, tenant_id, approved_by_user_id) → DeletionResult. In a single transaction: for each matched record, set is_deleted=True, write audit log entry with action='soft_delete'. Rollback on any exception.
6.2.5 Error Report Generation
Implement generate_error_report_xlsx(session_id, db) → BytesIO. Reads staging rows for the session where is_valid=False. Writes an .xlsx file: original columns + an 'Errors' column listing all field errors for that row. Returns bytes for streaming download.
6.2.6 Validation Gates (Phase 2 Checkpoint)
Unit test: validate_coordinates(200, 45) returns error; validate_coordinates(45.3, 6.2) returns valid.
Unit test: validate_row_splitter with splitter_level='first-level' returns error with exact message.
Unit test: run_full_validation on a 10-row test file with 2 intentional errors produces session with error_rows=2, valid_rows=8.
Unit test: commit_session inserts exactly valid_rows rows into the live table; staging rows marked committed=True.
Unit test: commit_session with a simulated DB error on row 3 rolls back all rows — zero rows in live table.
Unit test: generate_error_report_xlsx produces a valid .xlsx file with an Errors column.
PHASE 3  Upload API Router   [Sprint 2 — ~3 days]
6.3 Phase 3 Objective
Implement all upload and asset query API endpoints in router.py. Register the router in main.py before tasks_router.
6.3.1 Router Implementation Steps
Create backend/app/modules/infrastructure/router.py. Define infrastructure_router = APIRouter(prefix='/api/v1/infrastructure', tags=['infrastructure']).
Implement POST /upload/{asset_type}. Accept multipart/form-data with file field. Validate asset_type against allowed enum. Call validate_file(). On file error, return 422 immediately — do not create session. Create upload session record (status=PENDING). Call run_full_validation() synchronously (add async task queue support in Phase 7 if needed for large files). Update session to VALIDATED. Return session_id and validation summary.
Implement GET /upload/{session_id}/status. Return session state, counts, and summary. Used by frontend to poll for async validation completion.

9. Risks & Mitigations
Risk
Severity
Mitigation
PostGIS not enabled in production PostgreSQL
Critical
Verify in Phase 1 before any other work. Add a startup check in the application that raises a clear error if postgis extension is not found.
Large Excel files (5,000+ rows) causing timeout on synchronous validation
High
Phase 3: implement async task queue (Celery or FastAPI BackgroundTasks) for files > 500 rows. Frontend polls /status endpoint. Phase 1 works synchronously as MVP.
infrastructure_router catch-all routes shadowing existing task routes
High
Register infrastructure_router first in main.py. Add regression test that hits GET /api/v1/tasks/{id} and confirms it still routes to the task endpoint after infrastructure_router is added.
actor_label resolving as None in audit log (regression of full_name bug)
High
Enforce via code review checklist. Write unit test for audit_service.write_audit_entry with a user that has no staff_profile — confirm fallback to username.
Batch deletion file with thousands of keys causing slow matching queries
Medium
Use IN queries with chunking (1,000 keys per IN clause). Add index on box_id, tenant_id.
Excel file with merged cells or non-standard formatting breaking openpyxl
Medium
Use openpyxl in data_only mode, skip merged cells. Validate that row[0] is the expected header. Return clear error: 'File format not recognized — please use the provided template.'
Coordinate (0,0) incorrectly accepted for Nigerian infrastructure
Medium
The warning flag for (0,0) coordinates is logged in the session. Operations team is notified in the preview. Not a hard error — some edge-case valid coordinates near null island exist but are rare for Nigerian ISP infrastructure.
Approval of upload by different user than uploader causing audit confusion
Low
Log both submitted_by and approved_by separately in infrastructure_upload_sessions. Audit report shows both users.
ErrorBoundary not applied to new upload pages causing blank-page regression
Medium
PR review checklist item. Add automated Playwright/Cypress test that simulates a React render error in the preview table and confirms ErrorBoundary fallback appears.
